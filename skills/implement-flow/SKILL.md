# 実装フロー

設計書1件（＝並行可能な機能単位）ごとに回す。進行管理（ループ制御・受け渡し・完了判定）は必ずメインスレッドが行う。
サブエージェントはユーザーに確認できないので、判断が要る点は返してもらいメインがユーザーに確認する。

## 手順

1. リモートの main に未取得の更新がないか確認する。あれば pull して最新化する。
   ブランチ `dev/<作業概要>` 上で作業していることを確認する。
2. programmer に実装させる。**設計書のパス(または内容)とPJのCLAUDE.mdの場所を必ず渡す**。
   plan/ は gitignore 対象なので、worktree 等では存在しない場合がある。
3. reviewer にレビューさせる。変更ファイルと設計書のパスを渡す。
4. Important の指摘があれば programmer に修正させ、3 に戻る。
   - 修正と再レビューは最大3ラウンド。超えたら設計の見直しとしてユーザーに戻す。
   - 再レビューは差分のみ。修正済みの指摘は再掲させない。
   - 指摘は「直す」か「理由付きで却下」のどちらかで応答する。
   - reviewer の「Issue candidates」(スコープ外・既存の問題)は、PR 作成時にユーザーへ一覧で見せ、
     issue 化するか確認する(起票は合意を取ってから)。
5. tester に試験を実行させる。テストコマンドはPJのCLAUDE.mdに書かれたものを使わせる。
6. NG があれば programmer が修正し、3 に戻る（reviewer の確認 → tester の再試験）。すべて OK になるまで繰り返す。
7. 設計書の内容がすべて完了したら、設計書を `<設計概要名>.done.md` にリネームする。
8. メインがコミットし、dev/* ブランチを push する（1コミット1変更、git-workflow ルールに従う）。
   dev/* からの push は確認なしで行ってよい。main への push は禁止（hook が拒否する）。
9. main 宛てにプルリクエストを作成する。作成は確認なしで行ってよい。マージはしない。
10. **人間が**「マージした」と伝えたら、マージ後の片付けを行う（下記）。
    エージェントの承認は人間の承認にならない。マージ判断はユーザーが行う。
11. 不要なファイルを削除する。

## マージ後の片付け

ユーザーから「マージした」と伝えられたら、確認を待たずに次を順に行う。

1. 未コミットの変更がないか確認する（ある場合は破棄せず、内容をユーザーに見せて相談する）。
2. main に切り替えて pull する。
3. マージ済みの dev/* ローカルブランチを削除する。リモートブランチが残っていれば削除を試みる。
   失敗したら理由を報告する（GitHub 側で自動削除されている場合が多い）。
4. `<pjディレクトリ>/plan/<設計概要名>.done.md` があれば削除する。
5. リリース作業がある PJ（PJ の CLAUDE.md に記載）なら、リリースが必要か確認する。
6. 終了を報告する（実施内容を箇条書きで簡潔に）。

## 並行実行

- 依存関係がなく、編集対象ファイルが重複しない機能は並行して実施してよい。
- 同じファイルを触る可能性がある機能は直列で行う（並行編集の競合を避けるため）。
