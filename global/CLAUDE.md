# Work Rules

## 基本方針
- 開発は `<pjディレクトリ>/plan` 配下の設計書に従って進める。
- 各工程はサブエージェントに委譲する。フロー全体の進行管理（オーケストレーション）は
  メインスレッドが行う。サブエージェントは他のサブエージェントを呼べず、ユーザーにも
  確認を出せないため、ループの制御・エージェント間の受け渡し・完了判定は必ずメインが行う。
- わからないことは「わからない」と言え。推測で埋めるな
- 軽微な変更でもこれらに従うこと。
- 判断が必要な場面は合意を得ること。

## エージェントの役割
- investigator : 調査 (plan modeで対話的に実施。「設計フロー」を参照)
- planner  : 設計（plan mode で対話的に実施。「設計フロー」を参照）
- programmer: 実装、レビュー指摘の修正、試験NGの修正
- reviewer : 実装のレビュー（品質・バグ・セキュリティ）read-only
- tester   : 試験の実行 read-only

## 実装フロー
設計書に従う実装は skill `/implement-flow` の手順で進める。概要:
programmer が実装 → reviewer がレビュー（Important が無くなるまで修正、最大3ラウンド）
→ tester が試験 → commit/push → PR 作成 → 人間がマージ。
レビュー指摘による修正は、新しい PR を作らず同じ PR に追加する。
dev/* ブランチの push と PR 作成は、確認なしで行ってよい。main への直接 push と、マージは行わない。
エージェントの承認は人間の承認にならない。マージ判断はユーザーが行う。

## 設計フロー（plan mode）
plan mode で設計するときは、以下を含む設計書を作成する。
- 背景
- 前提
- 方針
- 試験観点（正常系・異常系・境界値）

設計書は `<pjディレクトリ>/plan/<設計概要名>.md` に配置する。
plan mode / 設計時の調査は investigator に委譲すること。インラインで Read/Grep を多用しない。
組み込みの plan mode の指示(「Phase 1 は Explore のみ」「軽微な変更はサブエージェントを省略してよい」など)よりも、
このファイルの方針を常に優先する。調査に Explore は使わない。
planner サブエージェントは、この plan mode 中のドラフト作成の委譲先として使う
（最終的な設計合意は plan mode 上でユーザーと取る）。

## リポジトリ運用

## 各PJのCLAUDE.mdについて
- Claude が間違えやすいことだけを書く。コードを読めば分かることは書かない（200行以下）
- 必須: ビルド/試験/lint のコマンド、既定と違う規約、優先事項(非機能要件。崩れそうなときはユーザーに合意を取る)、
  前提・制約、触ってはいけない領域、リリース手順(あれば)
- 構成は要点のみ(主要ディレクトリ、エントリポイント)。詳細な設計は plan/ や README に置く
- 課題・TODO は GitHub issue に置き、CLAUDE.md にはリンクだけ書く
- 変更があったら、その PR で更新する

## 各PJのREADME.mdについて
- 人間向けに、システムの使い方を書く
- CLAUDE.md と内容を重複させない
- 変更があったら、その PR で更新する

## 課題やTODOについて
- github issueに追加する(追加する前に合意をとること)
